# 授权群组自动参与与桌面控制台设计

## 背景与目标

本项目将从固定周期群发改为“授权群组内的低打扰自动参与”。所有目标群组均由使用者确认已获得管理员许可，并继续通过现有环境配置显式提供；系统不会发现、加入或向未授权群组发送消息。

目标包括：优先参与活跃对话、群聊冷场时有限度地主动发言、降低重复和无关内容、遇到投诉或管理员警告时自动停发，以及将现有 Web UI 重构为适合桌面浏览器的深色控制台。系统不提供隐藏自动化身份、绕过 Telegram 风控或规避群组管理的能力。

## 范围与非目标

范围内：

- 混合参与模式：回应活跃话题，并在冷场后生成主动发言候选。
- 全局参与参数、按群运行状态和按群每日计数。
- AI 生成优先，TXT 消息库兜底。
- SQLite 持久化、可解释决策日志和自动停发保护。
- A1 深色左侧导航仪表盘，仅以桌面浏览器为验收目标。

非目标：手机端完整适配、每群独立配置、引用回复、自动加入群组、恢复重启前尚未发送的候选消息。

## 架构

保留 Flask、Telethon、后台 asyncio 循环、`SendLoopManager` 状态机和 SSE。将目前集中在 `ui/send_loop.py` 的业务判断拆为以下独立组件：

- `ActivityObserver`：读取授权群组的新消息，维护最后活动时间，识别新话题和冷场。
- `ParticipationPolicy`：分类明确问题与普通讨论，应用参与概率、每日额度、冷场和重复规则。
- `SafetyGuard`：识别明确投诉、管理员警告、连续无人回应和人工暂停。
- `MessageGenerator`：根据最近上下文调用 AI；失败时从 TXT 选择，并执行空内容和重复检查。
- `StateStore`：使用 SQLite 保存每日计数、群组暂停原因、最后活动、最近发送和审计事件。
- `send_loop`：只负责编排上述组件、可中断等待、发送和状态通知。

处理流为：观察消息或检测冷场 → 生成候选 → 策略与安全校验 → 生成内容 → 等待 20–90 秒 → 再次校验 → 发送普通独立消息 → 持久化结果并通过 EventBus/SSE 更新前端。

## 参与规则

所有群组共用一套前端配置：

| 配置 | 默认值 |
|---|---:|
| 每群每日发送上限 | 30 条 |
| 冷场阈值 | 10 分钟 |
| 明确问题参与概率 | 70% |
| 普通讨论参与概率 | 15% |
| 发送前等待 | 20–90 秒 |

回应模式只处理上次观察后出现的非本人消息。AI 判断消息属于明确问题还是普通讨论，并判断内容相关性。概率通过后生成候选，但等待期间如果话题已经结束、额度耗尽、管理员发言、全局暂停或安全规则触发，则取消发送。

冷场模式仅在连续 10 分钟没有新消息时产生候选。如果本账号上一条消息仍未被其他群友的新消息覆盖，则不得再次主动发言。主动内容由 AI 根据最近上下文生成；仅在 AI 不可用时使用 TXT，且 TXT 同样受所有策略约束。

达到每日上限时，该群暂停至本地日期切换并自动获得新额度。连续两条已发送消息都没有其他群友后续发言时，该群暂停至次日。检测到管理员警告或群友明确表达“打扰、刷屏、停止”等投诉时，该群进入严重告警暂停，必须在前端人工检查并恢复。所有自动取消、跳过和停发均记录原因。

## 状态与持久化

全局继续使用现有启动、运行、暂停、停止和验证码等待状态机。每个群组另有观察、候选、等待发送、冷却、额度暂停、自动保护暂停和人工暂停等运行状态。

SQLite 写入必须与发送计数形成一致的临界区。每日计数、暂停状态和最近发送记录在程序重启后恢复；跨日额度按 Asia/Shanghai 本地日期计算。重启时不恢复未发送候选，所有群组重新进入观察状态。若 SQLite 无法可靠写入，系统停止新的发送并在前端产生高优先级告警，防止额度失真。

## 前端设计

采用 A1 深色控制台和固定左侧导航：概览、授权群组、参与策略、AI 与 TXT、实时动态、安全与审计、系统设置。

概览页顶部显示全局运行状态以及开始、暂停、恢复和停止操作；主体展示今日发送总数、观察中群组数、暂停群组数和下一候选倒计时。群组表显示每群状态、今日计数和最近决策。右侧“需要处理”区域突出严重告警，底部展示最近实时事件。

参与策略页集中编辑全局参数，不提供每群覆盖。输入概率必须为 0–100，时间范围必须有序，每日上限和冷场阈值必须为正数。离开存在未保存修改的页面时提示确认。严重告警只能从安全与审计页查看原因后人工恢复。SSE 断开时页面明显显示离线，但不影响后台任务；重连后回放近期事件。

## 错误处理

- AI 失败时使用 TXT；TXT 也不可用时跳过，不发送空消息。
- 网络错误有限次数退避重试；`FloodWait` 触发可中断的全局冷却，并严格等待 Telegram 指定时长。
- 配置非法时拒绝保存或启动，并返回字段级错误。
- 停止、人工暂停和等待均可中断；等待结束后必须重新执行策略与安全校验。
- 未识别异常记录完整日志，取消当前候选，不绕过额度或安全保护继续发送。

## 测试与验收

单元测试覆盖消息分类后的策略路径、固定随机源下的概率判断、冷场条件、每日额度、跨日重置、连续无人回应、投诉停发、重复过滤和等待后重新校验。集成测试覆盖 AI 到 TXT 的降级、SQLite 并发计数与重启恢复、暂停/恢复、`FloodWait`、SSE 重连回放以及配置 API 校验。

所有 Telegram 和 AI 调用使用 mock，自动化测试不得向真实群组发送。完整 `pytest tests/ -v` 必须通过。前端在 1440×900 桌面视口人工检查概览、配置、实时动态、严重告警、SSE 离线和重连状态。
